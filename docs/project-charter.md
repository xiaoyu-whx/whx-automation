**项目类型：** Android 自动化运行平台
**项目版本：** V1.0 立项版
**立项日期：** 2026 年 10 月 30 日

# 一、项目定位

## 1.1 项目目标

自主开发一套 Android 自动化工具，具备屏幕截图、图像识别、自动触控和脚本执行能力。

项目采用 PC 端开发、Android 端运行的模式。

所有编程、脚本编写、项目管理、调试、测试和 APK 构建工作均在 PC 上完成。

Android 端只负责运行已经编写好的脚本，不提供代码编辑器、编程环境或完整开发工具。

最终将自动化运行引擎打包为独立 APK，安装后可以脱离 PC 独立运行。

## 1.2 核心定位

本项目不是手机端编程软件，而是一个可以通过 JavaScript 控制 Android 设备的自动化运行平台。

目标参考：

- Auto.js：脚本自动化与 API 设计
- 按键精灵：自动化操作与任务执行
- 懒人精灵：图像识别与自动化能力
- 触动精灵：移动端自动化运行

不直接复制其他产品的实现，而是自主设计底层架构和核心功能。

## 2.1 Automation Core

负责自动化工具的核心能力。

包括：

- 屏幕截图
- 图像识别
- 触控操作
- JavaScript 执行
- API 调度
- 任务生命周期管理

核心模块尽可能独立于 APK 界面，方便后续复用和扩展。

## 2.2 Automation App

作为 Android 端运行载体。

负责：

- 权限申请和管理
- 脚本导入
- 任务选择和启动
- 运行状态展示
- 日志查看
- 暂停、继续、停止任务
- 后台运行和服务管理

不开发手机端代码编辑器，不承担 PC 端开发功能。

# 三、技术选型

| 技术 | 用途 |
|---|---|
| Java | Android 应用及自动化核心 |
| JavaScript | 用户自动化脚本 |
| QuickJS | Android 端 JavaScript 执行引擎 |
| TypeScript | 可选的脚本开发支持 |
| C++ | 性能敏感的底层图像处理 |
| JNI | Java 与 C++ 通信 |
| Android SDK | Android 系统功能调用 |
| Android NDK | 原生代码编译 |
| CMake | C++ 工程构建 |
| Gradle | Android 项目构建 |
| Git | 版本管理 |

### 技术原则

1. Java 负责 Android 应用、系统接口和核心调度。
2. JavaScript 负责用户脚本。
3. QuickJS 负责执行 JavaScript。
4. TypeScript 在 PC 端编译成 JavaScript，再交给 QuickJS。
5. C++ 只在确实存在性能收益时引入。
6. 简单图像识别优先自主实现，不急于引入完整 OpenCV。
7. 不使用 Lua 作为项目脚本语言。

# 四、核心功能设计

## 4.1 截图引擎

目标是稳定、快速地获取屏幕图像，并尽量减少资源消耗。

功能：

- 屏幕截图
- 连续截图
- 区域截图
- 截图缓存
- 图像资源复用
- 减少 Bitmap 和像素数组复制
- 支持不同截图后端

设计要求：

- 尽量避免重复申请截图资源。
- 支持连续识别场景。
- 避免无意义的高频截图。
- 控制内存占用。
- 不同设备使用可替换的截图实现。

## 4.2 图像识别引擎

这是项目的重点模块之一。

第一阶段实现：

- 单点取色
- 单点颜色判断
- 区域找色
- 多点找色
- 相似色识别
- 返回目标坐标
- 指定区域搜索
- 多目标搜索

第二阶段实现：

- 图片查找
- 模板匹配
- 图片相似度判断
- 多尺度模板匹配
- 更复杂的图像识别算法

设计要求：

- 优先保证准确性。
- 优化扫描速度。
- 支持限定区域搜索。
- 支持颜色容差。
- 减少不必要的图像复制。
- 对高频图像处理进行性能优化。

简单取色和找色优先自主实现；复杂模板匹配视实际需求决定是否引入 OpenCV。

## 4.3 触控引擎

实现 Android 自动化操作能力。

第一阶段：

- 点击
- 长按
- 滑动
- 连续点击
- 手势操作

第二阶段：

- 多点触控
- 复杂手势
- 触控任务调度
- 操作队列

触控后端采用可替换设计，根据设备环境选择合适的实现。

重点研究：

- AccessibilityService 手势接口
- Root 环境下的触控实现
- 不同模拟器和云手机的兼容性

注意：不同触控后端的权限、能力和限制不同，不假定所有 Android 设备都能使用相同方式。

## 4.4 JavaScript 脚本引擎

使用 QuickJS 作为 Android 端脚本执行引擎。

功能：

- 执行 JavaScript
- 多文件脚本
- 模块导入
- 脚本运行
- 脚本暂停与停止
- 异常捕获
- 运行日志
- API 调用
- 脚本任务管理

脚本在 PC 上编写和测试，最终以文件或项目资源的形式交给 APK 运行。

不要求用户在手机上编写代码。

## 4.5 JavaScript API

自主设计一套统一的自动化 API。

初步接口：

```javascript
// 截图
let img = captureScreen();

// 单点取色
let color = getColor(500, 800);

// 颜色判断
let result = isColor(500, 800, "#FFFF00");

// 找色
let point = findColor("#FFFF00");

// 区域找色
let point = findColor("#FFFF00", {
    region: [100, 100, 800, 600]
});

// 点击
click(500, 800);

// 长按
longClick(500, 800, 1000);

// 滑动
swipe(500, 1000, 500, 300, 500);

// 延迟
sleep(1000);
```

以上为接口设计示例，具体参数、返回值和异常规范在实际开发阶段确定。

API 应当保持统一、简洁，并为后续扩展保留空间。

# 六、脚本分发与 APK 运行方式

设计两种运行方式。

## 6.1 内置脚本模式

PC 将脚本和必要资源打包进 APK。

优点：

- 安装后直接运行。
- 不需要 PC。
- 适合固定用途的自动化小精灵。
- 可以发布独立成品。

## 6.2 外部脚本导入模式

APK 提供脚本导入与运行能力。

PC 编写脚本后，可以通过文件传输等方式将脚本交给 APK。

优点：

- 修改脚本不必每次重新编译 APK。
- 可以在同一个 APK 中运行不同任务。
- 方便脚本更新和维护。

两种模式共用同一套自动化核心。

手机端只负责导入、选择和运行，不提供代码编辑功能。

# 七、跨设备兼容

项目必须考虑三类运行环境。

| 环境 | 目标支持 |
|---|---|
| x86_64 Android 模拟器 | 必须支持 |
| ARM64 Android 云手机 | 必须支持 |
| ARM64 Android 真机 | 必须支持 |

主要开发和初期测试优先使用 x86_64 模拟器。

后续重点验证 ARM64 环境。

原生 C++ 库至少构建：

- x86_64
- arm64-v8a

Java 和 JavaScript 层尽可能保持统一。

注意：

- 截图接口可能因设备而异。
- 触控能力可能因权限和系统环境而异。
- 不同设备的 Android 版本可能影响后台运行。
- 不能仅凭模拟器测试成功就认定云手机和真机完全兼容。

# 八、性能目标

项目需要重视低配置设备的长期运行能力。

重点目标：

- 支持 1 核 1GB ARM64 云手机作为最低优化目标。
- 适配常见 2 核 2GB 云手机。
- 支持 x86_64 模拟器。
- 避免长期运行内存持续增长。
- 控制线程数量。
- 减少重复截图和图像复制。
- 提高高频找色的执行效率。
- 减少不必要的 CPU 占用。

优化原则：

1. 先测量，再优化。
2. 先确定瓶颈，再决定是否使用 C++。
3. 优先减少无效操作和内存复制。
4. 不为了追求技术复杂度而引入不必要的依赖。
5. 以真实设备的测试结果作为性能依据。

不要求在正式开发前系统学完 Java、Android 或 C++。

- 任务拆解
- 代码编写
