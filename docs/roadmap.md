阶段划分沿用项目书第九节。每阶段以**可验证的交付成果**结束；不达验收不进下一阶段。
所有性能目标都以本机实测基线为准，不用别人的经验值。

**实测基线（2026-10-30 · 雷电 9 · Android 9 · x86_64 · 720×1280）**

| 项 | 实测 |
| --- | --- |

| 9 条 evdev 事件写入 | 0.033ms |
| 完整 tap（按住 30ms） | 31.3ms |
| adb 对照：`screencap` / `input tap` | 141.6ms / 134.6ms |

## 阶段二 · 截图引擎 ✅ 已完成（2026-10-30）

| 任务 | 说明 |
| --- | --- |
| `helper` 启动链路 | assets 里的 helper dex → 释放到应用目录 → `su -c app_process` 拉起 |
| `ScreenSource` 接口 | `capture(region)` / `refresh()` / `available()` |
| `SurfaceControlSource` | 反射调用 + **HARDWARE 位图回读**（坑已踩过，见 architecture.md §5.1） |
| `Frame` 缓存 | 同帧复用像素；区域裁剪不复制整屏 |
| 传输实测 | 3.7MB 经 LocalSocket 的耗时；超 5ms 改 `SharedMemory` |
| 测量工具 | 连续 100 次抓帧的 P50/P99、内存占用 |

**交付**：可独立测试的截图模块。

**验收**
- 720p 截图 **P50 ≤ 20ms，P99 ≤ 40ms**
- 连续 100 次无全黑、无撕裂
- 区域截图耗时明显低于整屏
- 连续 1000 次抓帧后内存不增长（GC 后回到基线 ±5MB）
- helper 被杀后 App 自动重启它，30 秒内恢复

**实际结果（2026-10-30，雷电 9 / Android 9 / 720×1280）**

| 指标 | 实测 | 判定 |
| --- | --- | --- |
| 整屏抓帧端到端 P50 / P99 | **19.6 / 23.4 ms**（100 次） | ✅ |
| helper 内部：合成 / 回读 / 拷像素 | 3.3 / 6.0 / 3.7 ms | ✅ |
| 纯像素传输（3.5MB） | ≈ **4.9 ms**（约 730MB/s） | ✅ 不需要 SharedMemory |
| 区域抓帧 360×320 P50 / P99 | **13.9 / 16.3 ms**（0.44MB） | ✅ 明显低于整屏 |
| helper 启动+连接（含 su） | 249 ms | ✅ |
| ping 往返 | 0.06 ms | ✅ |
| 杀 helper 后自愈 | **124 ms** 恢复 | ✅ |
| 500 次抓帧后内存 | Java Heap 14.5MB → 10.7MB（GC 后下降） | ✅ 无增长 |

**踩坑记录（都已修）**

1. `NetworkOnMainThreadException`：UI 刷新时同步 ping helper 会崩。改为**状态缓存 + 后台探活**，
   `isAlive()` 只读缓存，`probe()` 才发网络请求。
2. **su 首次授权弹窗会阻塞 helper 启动**：连接超时从 6s 提到 **30s**，给用户点「允许」的时间；
   老式 Superuser 还会因为 manifest 没声明 `ACCESS_SUPERUSER` 报警告，已补声明。
3. **helper 不需要单独打包 dex**：`app_process` 的 CLASSPATH 直接指向 `base.apk` 即可加载类
   （实测通过），省掉一整套 resources→dex→assets 的构建工序。
4. **冷启动首帧有 300ms 级异常值**：区域截图首轮 P99 317ms，第二轮 16.3ms。
   属于首帧 GPU 路径冷启动，脚本层调用前应做一次预热帧。

**不做的事（实测后调整）**：原计划"LocalSocket 传输超 5ms 就改 SharedMemory" ——
实测 4.9ms，**不启用 SharedMemory**，保持 TCP 回环（跨 uid 不受 SELinux 限制，更稳）。

| 找图 40×40 | 6.5 ms，但**位置歧义** | ⚠️ 见下 |

**关键踩坑（已修）**

1. **粗筛 NCC 的统计量与采样步长不一致** → 匹配分数只有 0.436、位置乱跳。
   粗筛为提速用步长 2 采样图像，但模板的 ΣT、ΣT² 仍按全像素算，归一化对不上，
   相关性被亮度差主导。改成「统计量与采样步长严格一致」后分数回到 1.000。
   *这类 bug 不会报错，只会静默给错位置 —— 自检必须校验"能否找回原位"。*
2. **精修穷举太贵**：原本对每个候选在 ±9px 窗口内穷举（361 次 NCC），
   200×150 模板要 30ms。改成「爬山 + 只对最优候选做 ±2 小穷举」，降到 **16.3ms**。
3. **小模板会歧义**：40×40 的模板在四个按钮上像素完全相同时，得分 1.000 但位置不是原位。
   这不是算法错误，是模板本身不唯一。使用建议：模板要选**有文字或图标**的区域，
   面积别小于 60×40。

**结论**：纯 Java 全部达标，**不需要 JNI/C++，也不需要 OpenCV**。

| 项 | 实测 | 判定 |
| --- | --- | --- |
| 单次点击（hold 30ms） | P50 **32.1 ms** / min 30.9 ms | ✅ ≤40ms |

| 输入设备探测 | `/dev/input/event2` absX=1279 absY=719 slot=15 | ✅ |

**踩坑记录（最重要的一条）**

**轴坐标不需要交换 —— 早期判断是错的。** 我根据 `absX=1279 ≈ 屏幕高 1280` 推断
"面板是横屏坐标、必须交换"，加上交换后坐标落到窗口外，表现为**只收到 ACTION_DOWN、
收不到 ACTION_UP**，按钮完全不响应，且不报任何错。

定位手段：在 Activity 里挂 `OnTouchListener` 打印收到的事件坐标，一次注入就反推出真实映射：

```
注入 raw(X=463, Y=114) → 收到 (260, 154)
260 = 463/1279×720   154 = 114/719×1280 − 状态栏
```

结论：框架对**每个轴各自**按 absMax 缩放到屏幕对应维度，恒等映射 + 比例缩放即可。
代码里保留 `swapAxes` 开关（默认 false），供个别面板方向不同的设备使用。

**其它**
- 首次点击 177ms：`getevent -pl` 探测 + 打开设备节点，属一次性开销；脚本层应在启动时预热一次。
- `input keyevent` 走的是 shell（134ms 级），阶段八再优化成直写按键节点。

**踩坑记录**

1. **QuickJS 只能绑定接口**：`set(name, type, instance)` 传具体类会抛
   `Only interfaces can be bound`。解法：定义 `JsApi` 接口，实现类实现它，绑定接口。
2. **把方法赋值给全局变量会丢代理**：`var log = api.log` 之后调用报
   `Null Java Proxy`。必须生成包装函数 `function log(m){ return api.log(m) }`，
   保证调用时 `api` 仍作为接收者。
3. **JS 不会自动把字符串转 double**：`click("360","640")` 抛
   `Cannot convert value 360 to double`。脚本侧要 `Number()` 转换。
4. **日志区把按钮顶出屏幕**：早期把脚本日志写进顶部状态栏，长脚本运行时
   「停止脚本」按钮被一路顶下去、**根本点不到**。改为按钮下方独立的固定日志区。

完全不同，只有换算正确才会落在同一点。实测通过，说明 `axisX = x * absMaxX / (screenW-1)`
这套比例映射是对的。

**优化结论**

- 瓶颈已完全落在平台侧：截图 ~20ms + 点击按住 30ms 是硬下限，**不需要 JNI / C++**。
- 想再快只有两条路：缩短按住时长（25ms 起风险变大）、或降低截图分辨率（牺牲识别精度）。

## 风险与对策（对齐项目书第十一节）
