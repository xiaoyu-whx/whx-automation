# 路线图

阶段划分沿用项目书第九节。每阶段以**可验证的交付成果**结束；不达验收不进下一阶段。
所有性能目标都以本机实测基线为准，不用别人的经验值。

**实测基线（2026-10-30 · 雷电 9 · Android 9 · x86_64 · 720×1280）**

| 项 | 实测 |
| --- | --- |
| `SurfaceControl` 截图 720p | 11.4ms（合成 3.5 + 回读 5.7 + 拷 2.3） |
| 9 条 evdev 事件写入 | 0.033ms |
| 完整 tap（按住 30ms） | 31.3ms |
| adb 对照：`screencap` / `input tap` | 141.6ms / 134.6ms |

## 阶段二 · 截图引擎

| 任务 | 说明 |
| --- | --- |
| `helper` 启动链路 | assets 里的 helper dex → 释放到应用目录 → `su -c app_process` 拉起 |
| `ScreenSource` 接口 | `capture(region)` / `refresh()` / `available()` |
| `SurfaceControlSource` | 反射调用 + **HARDWARE 位图回读**（坑已踩过，见 architecture.md §5.1） |
| `Frame` 缓存 | 同帧复用像素；区域裁剪不复制整屏 |
| 传输实测 | 3.7MB 经 LocalSocket 的耗时；超 5ms 改 `SharedMemory` |
| 测量工具 | 连续 100 次抓帧的 P50/P99、内存占用 |

**交付**：可独立测试的截图模块。

**验收**
- 720p 截图 **P50 ≤ 20ms，P99 ≤ 40ms**（helper 侧已实测 11.4ms，加上传输要守住 20ms）
- 连续 100 次无全黑、无撕裂
- 区域截图（只抓 720×640）耗时明显低于整屏
- 连续 1000 次抓帧后内存不增长（GC 后回到基线 ±5MB）
- helper 被杀后 App 自动重启它，30 秒内恢复

## 阶段三 · 图像识别引擎

| 任务 | 说明 |
| --- | --- |
| 取色 / 颜色判断 | `getColor` / `isColor`，容差可配 |
| 找色 | `findColor` / `findColorAll`，支持区域、扫描方向、步长 |
| 多点找色 | `findMultiColor`（锚点 + 偏移色） |
| 模板匹配 | 金字塔 + 归一化互相关 + NMS，分辨率自适应 |
| 性能 | 区域限定、行连续访问、避免 `getPixel` 逐点 JNI |

**交付**：可实际使用的识别模块。

**验收**
- 单点取色 **≤ 0.05ms**
- 720p 全屏找色（1 个目标，step=1）**≤ 15ms**
- 720p 单尺度模板匹配 **≤ 20ms**；内存不随调用次数增长
- 1 核 1GB 场景：全屏找色 step=2 时 **≤ 10ms**
- 若这些目标用纯 Java 达不到，**才**评估 JNI/C++（项目书原则：先测再优化）

## 阶段四 · 触控引擎

| 任务 | 说明 |
| --- | --- |
| `InputBackend` 接口 | `tap` / `swipe` / `path` / `key` / `available` |
| `EvdevInput` | 探测触摸节点与 `absmax`；**轴坐标交换**；24 字节事件直写 |
| 手势 | 直线、贝塞尔曲线多点、连续点击 |
| 调度 | 单线程串行队列 + 最小间隔 + 随机抖动 |
| 后端调研 | 记录 Accessibility / MediaProjection 的可行性与代价（只记录，不实现） |

**交付**：能独立执行自动化触控操作。

**验收**
- 单次点击 **P50 ≤ 40ms**（实测 31.3ms，含按住 30ms）
- 连点 20 次/秒，目标 App 100% 收到
- 滑动轨迹与请求点误差 ≤ 2 帧（用 `getevent` 录制比对）
- 1000 次点击后坐标不漂移；节点号变化能自动重新探测
- 屏幕坐标 → 轴坐标的换算在 720×1280 与 1080×1920 上都正确

## 阶段五 · 脚本执行引擎

| 任务 | 说明 |
| --- | --- |
| QuickJS 集成 | AAR 引入或自行编译（阶段五第一件事就是验证可行性） |
| JS ↔ Java 桥 | 绑定 `captureScreen` / `getColor` / `click` 等；**每次调用开销必须实测** |
| 脚本线程 | 独立线程 + 停止标志 + 中断回调 |
| 生命周期 | 运行 / 暂停 / 停止 / 异常捕获 / 日志回传 |
| 多文件 | `import` 相对路径模块；脚本包目录结构固定 |

**交付**：APK 能运行 PC 编写的 JavaScript 脚本。

**验收**
- 示例脚本跑通：截图 → 找色 → 点击 → 校验
- 单次 API 调用桥接开销 **≤ 0.5ms**（不含操作本身）
- `stop()` 后 1 秒内脚本线程退出，无残留
- 脚本抛异常时，日志里有文件与行号
- 1000 次 API 调用后内存不增长

## 阶段七 · 跨架构适配

| 环境 | 目标 | 重点风险 |
| --- | --- | --- |
| x86_64 模拟器（雷电 9） | 已跑通 | — |
| ARM64 云手机 | 必须支持 | 虚拟化输入可能看不到触摸节点；截图 API 差异 |
| ARM64 真机 | 必须支持 | SELinux 策略、su 实现差异、后台限制 |

**交付**：支持目标设备的跨架构版本。

**验收**
- 三端都能：截图、点击、找色、跑脚本
- 每端的实测延迟记录在案（不达标就优化，不靠"应该差不多"）
- 差异点写进文档（哪个设备需要哪个后端）

| 任务 | 说明 |

## 风险与对策（对齐项目书第十一节）

| 风险 | 我们的实测认知 | 对策 |
| --- | --- | --- |
| Android 截图限制 | 雷电无 fb0；普通 App 无 `READ_FRAME_BUFFER` | helper 进程 + `ScreenSource` 多后端 |
| 触控权限限制 | evdev 需 root；`input` 命令慢 4 倍 | `InputBackend` 抽象，v1 只做 root |
| 模拟器与真机差异 | 仅模拟器验证过 | 阶段七分设备验证，逐项记录 |
| ARM64 兼容 | Java 层天然兼容；C++ 才需要 NDK 矩阵 | 能不引 C++ 就不引 |
| QuickJS 桥接 | 每次调用开销未知 | 阶段五第一件事就是测 |
| 低配内存不足 | 未验证 | 帧缓存 + 显式回收 + 24h 长跑 |
| 长时间运行异常 | 未验证 | 阶段八专项 |
